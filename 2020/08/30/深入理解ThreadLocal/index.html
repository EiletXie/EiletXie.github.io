什么是ThreadLocal？

​ 在Java中，ThreadLocal是一个类，此类提供线程局部变量，每个线程都有自己的独立的、初始化的变量副本，对于这些局部变量的访问是通过 get/set方法来获取。

简单点说，我们平时创建的成员变量是线程不安全的，然而，只要是 ThreadLocal变量，它是属于线程私有的，在多线程环境中，即使多个线程同时访问此变量，其内部也做了隔离,现在可以大致的理解为其内部是一个 HashMap，key为 线程ID，value为 我们所存放的值。 有点类似我们去超市的时候，将自己一些东西放到储物柜里，每个人都有自己专属的条形码和柜子。

ThreadLocal有什么特性，可以用来做什么？

​ 我们用一个工具来干活，肯定是因为它具备某些特性，能够匹配特定的场景。那么ThreadLocal它的特性有哪些？


ThreadLocal只初始化一次变量

从该initialValue方法注释中，我们可以得知 正常来说，在一个线程中，这个 initialValue 方法最多只会在第一次调用get方法时执行一次，后续不会再重复执行，并且通常以匿名内部类的方式覆盖实现

这就体现出它的作用，如果 一个线程在处理多处代码逻辑，需要经常创建一些常用辅助对象时，完全可以在 initialValue 方法中 提前初始化，从而避免重复创建对象。


举个栗子

​ 我们平时系统开发中，如果某块业务的处理逻辑涉及到多个方法的日期处理，那么我们完全可以在 initialValue中创建 SimpleDateFormat 对象，这样我们就不用在每个方法中都创建一个 SimpleDateFormat 对象了，它不香吗？

​ 当然SimpleDateFormat 属于小对象，你如果在这个线程的生命周期中都没有涉及大量创建，那确实没有特别明显的优势，如果是一个大对象呢？那么存在线程中只创建一次，还是懒加载，它一定会比 从缓存中或者数据库中去频繁的读取的方式要高效，节省性能开销。

​ 又或者是一些框架设计时，如 jdbc连接池，一些持久层框架 如 Hibernate 它就是将 connection存放在ThreadLocal 中，那可真是一次创建，长期使用。


我们总结了第一个用处

用处1：对象可以在initialValue只初始化创建一次，适用于业务处理中涉及经常需要使用辅助对象的场景

ThreadLocal最大的特性是什么？

线程私有的局部变量呀，至于怎么做到的，在下一个章节 关于 ThreadLocal的设计原理说明，这里先说说这个特性意味着什么，匹配哪些场景。


我在知乎上看到了这样一段话：

当你在一个类中使用 static 成员变量时，一定要问自己这 个 static 成员变量需要考虑“线程安全吗？”（也就是说多个线程需要自己独立的 static 成员变量吗？）如果需要那就需要使用ThreadLocal

其实说的就是 如何将 线程共享的static变量变成 线程私有的场景。因为static修饰的变量是存储在方法区，方法区是线程共享的。

那么在实际生活的系统场景下，用户登录时的session管理，其实也是可以用 ThreadLocal

在当前线程中存储用户信息，处理完当前的部分业务逻辑，再get取出来传递。

这样做的好处就在于减少了将用户信息在不同的场景下传递次数，一定程度降低了代码的耦合性。

（当然复杂的业务逻辑不可能只用一个线程就解决了，所以只能说一定程度。。）


总结一下特性

1、只初始化一次变量，懒加载，减少对象的创建开销

2、线程私有的局部变量，保证线程安全的同时，减少了信息的传递开销，一定程度可以降低代码的耦合性

这里抛出一个问题，为什么 ThreadLocalMap 存储的是一个 Entry数组，而不是一个 简单的Entry对象？

​ 因为你业务代码能new好多个ThreadLocal对象，各司其职。但是在一次请求里，也就是一个线程里，ThreadLocalMap是同一个，而不是多个，不管你new几次ThreadLocal。

​ ThreadLocalMap在一个线程里就一个，因为ThreadLocalMap的引用是在Thread里的，所以它里面的Entry数组存放的是一个线程里你new出来的多个ThreadLocal对象。

1、和Synchronized的区别

问：他和线程同步机制（如：Synchronized）提供一样的功能，这个很吊啊。

答：否！同步机制保证的是多线程同时操作共享变量并且能正确的输出结果。ThreadLocal不行啊，他把共享变量变成线程私有了，每个线程都有独立的一个变量。举个通俗易懂的案例：网站计数器，你给变量count++的时候带上synchronized即可解决。ThreadLocal的话做不到啊，他没发统计，他只能说能统计每个线程登录了多少次。


2、存储在jvm的哪个区域

问：线程私有，那么就是说ThreadLocal的实例和他的值是放到栈上咯？

答：不是。还是在堆的。ThreadLocal对象也是对象，对象就在堆。只是JVM通过一些技巧将其可见性变成了线程可见。

4、会导致内存泄漏么

问：会导致内存泄漏么？

答：分析一下：

  • 1、ThreadLocalMap.Entry的key会内存泄漏吗？
  • 2、ThreadLocalMap.Entry的value会内存泄漏吗？

先看下key-value的核心源码


先看继承关系，发现是继承了弱引用，而且key直接是交给了父类处理super(key)，父类是个弱引用，所以key完全不存在内存泄漏问题，因为他不是强引用，它可以被GC回收的。

弱引用的特点：如果这个对象只被弱引用关联，没有任何强引用关联，那么这个对象就可以被GC回收掉。弱引用不会阻止GC回收。这是jvm知识。

再看value，发现value是个强引用，但是想了下也没问题的呀，因为线程终止了，我管你强引用还是弱引用，都会被GC掉的，因为引用链断了（jvm用的可达性分析法，线程终止了，根节点就断了，下面的都会被回收）。

这么分析一点毛病都没有，但是忘了一个主要的角色，那就是线程池，线程池的存在核心线程是不会销毁的，只要创建出来他会反复利用，生命周期不会结束掉，但是key是弱引用会被GC回收掉，value强引用不会回收，所以形成了如下场面：

Thread->ThreadLocalMap->Entry(key为null)->value

由于value和Thread还存在链路关系，还是可达的，所以不会被回收，这样越来越多的垃圾对象产生却无法回收，造成内存泄漏，时间久了必定OOM。


解决方案: ThreadLocal已经为我们想好了，提供了remove()方法，这个方法是将value移出去的。所以用完后记得remove()。

6、ThreadLocal里的对象一定是线程安全的吗

未必，如果在每个线程中ThreadLocal.set()进去的东西本来就是多线程共享的同一个对象，比如static对象，那么多个线程的ThreadLocal.get()获取的还是这个共享对象本身，还是有并发访问线程不安全问题。

说说为什么是空指针？

因为你get方法用的long而不是Long，那也应该返回null啊，大哥，long是基本类型，默认值是0，没有null这一说法。ThreadLocal里的泛型是Long，get却是基本类型，这需要拆箱操作的，也就是会执行null.longValue()的操作，这绝逼空指针了。
