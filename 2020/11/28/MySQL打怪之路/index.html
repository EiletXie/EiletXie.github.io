MySQL打怪之路

发表于 2020-11-28 分类于 数据库优化 阅读次数： 本文字数： 4.3k 阅读时长 ≈ 4 分钟

​

​ 最近花时间看了一部分的《高性能MySQL》 红宝书，以及 丁奇大佬的 《MySQL实战45讲》，对 MySQL的理解又加深了不少，要保持日常MySQL的高性能，避免犯一些低级错误，需要我们对 MySQL的体系结构、逻辑设计、每个模块都有一定的理解，这里便萌生了写几篇总结的博客的想法。

​ 计划是针对各个重要的模块分别做 知识点总结以及高性能需要注意的点的阐述。当前的这篇就做一个全篇的概述吧，针对一个开发日常面对MySQL如何保证整体的高性能，需要注意哪些坑。


接下来我最主要概述以下几点

  • MySQL的逻辑架构
  • 什么才是日常开销最大的地方？
  • MySQL因此做了哪些措施？
  • 索引必须了解的知识
  • 安全性是如何保证的？

​ MVCC事务多版本控制、索引、日志系统的设计都是很大一块的内容，也是核心，后续我会一一补充上来，这里暂时不做详细说明。


MySQL的逻辑架构

上图是对 一个查询语句在MySQL中需要经历哪些模块

在MySQL中主要分为两大模块 Server层和引擎层

客户端

Server层（在内存中操作）

  • 连接器： 用户权限校验
  • 缓存：对操作语句涉及加载的数据存储在内存中
  • 分析器： 对sql语句的词法、语法校验
  • 优化器：sql优化，提供自己认为最佳的执行方式
  • 执行器：操作执行引擎并返回结果

引擎层（在磁盘中操作）

大家知道sql语句会涉及哪些模块，这些模块有哪些用即可，不需要做过深的研究。


什么才是日常开销最大的地方？

​ 在MySQL中单论各模块的执行，什么是开销最大的呢？是对磁盘的读写，也就是IO开销最大，首先我们要知道数据是存储在磁盘，而磁盘的数据分布在各个数据页中，页（Page）是 Innodb 存储引擎用于管理数据的最小磁盘单位，一个数据页为 16 K。假设一行数据记录为16字节，那么一个数据页最多可以存放1024条记录（不考虑数据空洞的情况）。

​ 我们必须要明白一点，那就是不管你是用索引(主键索引、普通索引、覆盖索引）还是全表扫描，只要你所需的数据没有在缓存中命中，你就必须去磁盘中加载数据页，把一页数据页里的数据记录加载到内存中进行遍历来找到对应的记录，MySQL的索引通过B+树的结构保证数据能在3次左右的磁盘IO读取便能定位到一条数据所在的磁盘数据页位置。

​ 大家对索引的B+树结构和磁盘数据页不太理解的话，可以看往期的文章 MySQL的索引模块，这里不做过多说明。

​ 因此我们日常要注意的和MySQL所要做的都是尽可能的减少 磁盘的读写，在内存中进行操作或者业务的设计来尽量避免大量IO读写数据。


那么MySQL是怎么设计来减少磁盘读写的呢？

1、通过缓存命中来减少磁盘读

​ 假设表A是在系统的很多业务模块都会被用到，即表A经常要被查询，比如系统配置、用户信息等，难道每次都去数据库查吗？肯定是加载到缓存中，如果缓存中有直接返回结果来减少IO开销的。


2、通过change buffer来减少磁盘写

​ 既然可以通过缓存记录数据，减少去磁盘读取，那能不能有一种方式在缓存中记录客户端的更新语句，等到合适的时候再写入到磁盘中，假如这个时候要查询数据，先加载磁盘中的数据到缓存，再将更新语句逻辑merge到对应的数据记录中，然后返回结果。没错，MySQL就有这种东西，叫做change buffer。

​ 这里需要说明change buffer是什么？ （mysql5.5之前只支持记录插入语句，又称为insert buffer,mysql 5.5以后支持更新和删除语句的记录）。

​ 我们看一下MySQL官网5.7版本对于 change buffer的说明


​ change buffer是一种特殊的数据结构，用于在二级索引页不在缓冲池中时将更改缓存到二级索引页（非聚簇索引即非主键索引，这里你直接理解成普通索引和数据页就行，因为我们要更新的就是这些数据）。缓冲的更改（可能由INSERT，UPDATE或DELETE操作（DML）引起）将在以后通过其他读取操作将页面加载到缓冲池中时合并。


​ 可能你还不能理解，我这里举一个例子，假设 一个用户行为记录分析表，它的数据是经常需要更新的，当用户做了几百次操作，如果没有change buffer，你需要读取一次索引对应磁盘数据页到内存中，更新了再写入到磁盘中，重复上百次。这里你需要明白一个机制（如果表更改了，那么使用这个表的所有缓存查询将不再有效，查询缓存中值相关条目会被清空，这是为了保证数据的一致性）

​ 这个时候你就明白change buffer的作用了，它不仅减少了随机的磁盘写，转变成了顺序磁盘写，某种意义上如果是重复数据的更新，也减少了磁盘读。


细心的读者会发现，光有change buffer是不行的，因为一旦MySQL异常重启，岂不是缓存中的数据会全部丢失? 这就得用到 redo log,如果发生异常的情况，会根据redo log做数据的更新，那如果 是刚写入change buffer，还没有写入到 redo log的时候挂掉了咋办？

​ DML语句是会开启事务的，只有redo log成功写入提交后，当前事务才会commit的，如果redo log没写就失败是会直接回滚事务的，又或者服务端挂掉则缓存清空，redo log没有记录到对应更新而已，这种情况需要重头再来，不会导致数据不一致的。


索引小知识

​ 大家都了解，索引就像是书的目录，是为了快速查找数据。它是由B+树的结构，正常的业务在亿级别以下的表，能够做到3次查询即可找到对应的数据页。

​ 但是索引也可能因为你的查询方式，或者一些限制因素从而失效，或者Mysql选错了索引等。

​ 关于查询方式不对导致未使用到的索引的情况有很多，范围查询，类型转换（尤其是很少注意的隐式转换），使用内置函数，复合索引查询条件顺序不对等等。这是一块很大的内容，这篇文章只讲总览，就不针对性的说，大家这方面不太了解的，我推荐可以学习B站上 尚硅谷的Mysql高级篇，那个视频对这块有比较详细的讲述。

​ 我这块说和大家说的是一些平时很少会注意的点。


普通索引和唯一索引的区别

​ 唯一索引要求 数据列组合的值是唯一的，普通索引没有这个要求，这个大家都知道。还有呢？大家有没有想过，这两种索引对DML语句有什么影响吗？

对SELECT语句来说：

如果是等值查询，在索引遍历时，找到符合要求的记录后，唯一索引是不需要往下遍历，因为只有一条主键ID，而普通索引可能存在多条，需要继续遍历，直到找到的数据记录不符合要求为止，不过这个对性能几乎没有影响。


对UPDATE、INSERT语句来说：

​ 这就是考察大家的地方，我们前面说过 change buffer。再回顾一下它的作用，把用户的非SELECT的DML语句记录到缓冲池，当读取对应表记录到缓存时，将顺序的把这些DML语句执行更新该记录，然后再写回数据页，大大减少了磁盘读和磁盘写。

​ 如果是唯一索引，能不能将INSERT语句缓存起来，作为change buffer呢？明显不能，为什么？

​ 因为表里面可能已经存在对应的数据，你必须去查表判断唯一性，而普通索引则没这个必要，这就是我们需要注意的区别。

​ 那你此时还有疑问，那为什么UPDATE语句也不能作为change buffer呢？

​ 一样的数据列唯一性问题，唯一索引又不一定非得是主键索引，假设我设置唯一索引列是name,update user set name = ‘李四’ where name = ‘张三’ ，你必须在更新前去数据库查询索引判断name=’李四’存不存在。


Change Buffer的适用场景

​ change buffer是将更新语句存储在缓冲区中，当执行读取语句时再将对应的更新语句顺序更新，这个操作叫merge，然后刷回磁盘。这种是特别适合写多读少的场景的。

​ 但是如果是读多写少的场景或者是写完马上就要读的场景，这种情况其实是不适合的，将更新先记录在 change buffer，但之后由于马上要访问这个数据页，会立即触发 merge 过程。这样随机访问 IO 的次数不会减少，反而增加了 change buffer 的维护代价。所以，对于这种业务模式来说，change buffer 反而起到了副作用。


字符串加索引注意点

​ 如果你需要给一个邮箱或者是身份证号加索引，你怎么加好呢？索引是有开销的，如果你就按照整个身份证号来存，开销较大，在一些业务场景下，有很多东西是没必要存的。

​ 假设你只需要记录某个县的居民身份证号，那前面的6位是地址码，就不用记录。又例如记录某个公司的用户邮箱 后缀.com是不是可以去除，其实在某些情况下我们如何取字符串作为索引，一个是通过先去除无用的字符，二是通常查询来判断

​ 使用前缀索引，定义好长度，就可以做到既节省空间，又不用额外增加太多的查询成本。

我们可以截取对应长度的字段来判断区分度

当然，使用前缀索引很可能会损失区分度，所以你需要预先设定一个可以接受的损失比例，比如 5%。然后，在返回的 L4~L7 中，找出不小于 L * 95% 的值，假设这里 L6、L7 都满足，你就可以选择前缀长度为 6。

​ 当然你也可以考虑使用其他的方法来保证区分度。


hash对应字段的值作为索引

​ 这种在很多业务上都经常见到，我举一个我公司的例子，假设我要确定相关的记录，没法通过主键id去找，我在业务流的上面中只能获取十几个字段的值，怎么快速找到下面业务流中符合要求的数据呢？ 我们在业务的设计上，在插入记录时新增一个 hash字段，将这十几个字段的值组合成一个字符串然后hash出一个值存储。这样我们在查找时在应用层直接算出hash值就能够根据hash值建的索引进行快速查找，避免了全表扫描。


倒序存储

​ 这种业务上遇到的不多，例如身份证号前面的区分度很低，我们可以倒序的然后查询区分度，选择保留的长度，裁剪字符串，然后再存起来。


安全性问题

​ 安全性问题涉及 主备同步、crash-safe，其实需要了解的还是日志的设计，redo log（重做日志），binlog(归档日志）

​ redo log在许多应用场景中一般只存储DML语句执行后的结果值，binlog是详细记录了sql语句，通过这两黄金搭档来保证crash-safe和主备同步。后续会单独写一篇博客，一是涉及内容过多，二是我现在也不能说对其完全了解，尤其是其结构设计这块。
