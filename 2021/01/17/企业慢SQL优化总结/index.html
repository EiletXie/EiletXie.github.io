企业慢SQL优化总结

发表于 2021-01-17 更新于 2021-01-20 阅读次数： 本文字数： 4.9k 阅读时长 ≈ 4 分钟

前言： 最近由于组内大佬出差，我临时顶替来处理我们项目组修复慢SQL缺陷的任务，抱着头大和觉得能学到东西快乐的心情弄了2周，有一些总结和心得在此记录一下。


处理的流程简要如下：

1、公司检测超过指定时间的慢SQL，生成缺陷BUG发送给对应项目组

2、开发拿到性能缺陷Bug，通过关键词查询对应环境的Monitor日志信息定位具体业务场景

3、查看explain执行计划和 SQL语句的使用场景，进行分析和修复


慢SQL类型

我在处理的过程中发现企业中的慢SQL基本分为3种类型

1、一些核心数据的统计业务

例如：各应用首页的数据统计展示，用户数据及核心表数据的分析

特点：查询条件比较模糊，查询数据量较大

解决方式： 这种是比较头疼的，目前我和同事讨论的解决方式有几种

    • 如果查询的数据是用户特有的，数据变化不大，实时性不强的查询业务产生。那么使用缓存机制，每隔1小时查询一次放入Redis中，设置过期时间。
    • 如果查询的数据是实时性很强的，这就是头疼的地方，我们的核心业务在目前的情况数据量已经达到数百万级，这种暂时是考虑业务上优化，精确查询的范围，并将核心的数据表进行水平分表。
    • 加入慢SQL黑名单，暂时忽略它

2、报表查询

报表是企业中使用很多的地方，是用来统计不同业务的用户数据。例如：当前组织的入库、出库的物料、金额汇总，物料的账龄等等

特点： 联查的数据表很多，尤其是考虑不同国家的多语言的情况，联查的数据表可能翻倍。Join表可能会出现type=ALL的全表扫描情况，或者是使用 BNL(Block Nest-Loop Join)算法和NLJ(Index Nest-Loop Join)算法


遇到的问题：

Join联查的表明明有索引，但是走的是全表扫描

这种可能有多种情况

1、驱动表A与被驱动表B的联查字段的类型或者双方的字符集不一样导致的

这种情况下数据库会隐式转换类型来匹配，从而索引失效了，通常开发是不会犯字段类型不一样的这种比较低级错误的，大多数情况下是因为历史升级的原因导致了两个表相关字段的字符集不一致。

2、联查的数据表其要查询的数据列很少，并且数据记录很多，查询到对应的主键索引ID再查询所需记录的性能不如直接全表扫描

​ 例如 Select A.*,B.age from A join B on A.name = B.name and B.local = ‘ZH_cn’ 这种，如果走B.name索引，那么需要通过B.name的索引找到记录的主键索引ID，通过该ID找到主键索引对应的记录所在的物理页，取出该记录下的age字段。

​ 这样会导致一个问题，就是B.name索引顺序扫描读取的主键ID集合不是有序的，会造成随机读盘，这样效率不高，如果B表中有相关一部分比例是匹配的，那么优化器会认为全表扫描的顺序读盘效率更高，从而使用全表扫描的策略。

解决办法：

    • 在确定大部分是这种场景下，可以扩展原来的 B.name索引为联合索引 IDX_B(name,local)、
    • 开启MRR，这种权限不是普通开发能接触到的，暂时忽略，关于MRR，下面我会说明。

3、普通业务SQL

这种导致性能慢的原因有很多，常见的有 未使用索引、复合索引未遵循最左匹配，二开业务的字段与联查表字段类型不一等

1、未使用到索引

​ 这种情况比较好解决，可以考虑使用的频率，以及联查字段的区分度考虑是否需要添加索引，或者 如果该联查多字段顺序类型的场景比较频繁，可以考虑扩展索引成复合索引。

​ 需要注意的地方是，小表的全表扫描其实影响不大。一个只有几百的某些全局配置表，logN与N几乎处于同一个数量级，要思考其他导致慢SQL的原因。尽量小表驱动大表，虽然这个通常在业务上很难做到。

2、复合索引未使用最左匹配导致索引失效的

​ 这种情况如果你公司使用的是普通的查询SQL，不是ORM其实都很好解决，调整SQL中匹配的字段顺序即可，但是在ORM中其实是不太好解决的。

3、二开业务慢SQL

​ 在确定不是自身业务导致慢SQL的情况下，转给二开部门来处理。


一个有趣的问题

where中 in 一个大的list集合，与将 list存储在一个临时表来 join联查匹配，这两种方式，哪个更快？

​ 我在一些慢SQL中发现公司平台有将 where in list 转换为 join 临时表 on 来进行处理，这引起了我的兴趣。这两种方式，哪种更好呢？我觉得需要分情况讨论，在stackoverflow中也有对这个问题的讨论，感兴趣的同学也可以搜搜。

1、如果 where in list 中，list集合会经常改变，并且该慢SQL执行频率高

​ 这种情况，我认为是使用 where in list 整体对系统影响较小，因为频繁的创建和销毁临时表对整个系统的性能是有一定影响的。并且在实现上，完全可以将list的数据在业务代码中进行判断，通过内存来过滤，效果更佳。

2、如果 list集合很大，并且对应慢SQL执行频率很低。

​ 这种情况，应该是创建临时表的性能更佳，假设list有10万数据，通过临时表 + 创建临时表索引联查的方式，与 where in list 相比，是 logN VS N的时间复杂度，但注意，要list集合很大才有性价比。

Join相关知识

在慢SQL中大部分情况都是有联查表处理的，掌握Join相关的知识对整体慢SQL的解析有一定的帮助，这边来说说我最近学习总结到的Join知识。

在下面的SQL语句中，创建X，Y表，Y表和X表结构一样，X表插入一千条数据，Y表插入一百条

由于在日常业务中，绝大数情况都是使用left join，并且是大表联查小表,这里就以 left join举例， 在下面语句中，x为驱动表，Y为被驱动表

当驱动表联查被驱动表，并且使用到了被驱动表的索引，这种场景被称为 NLJ

NLJ(Index Nest-Loop Join)

执行过程如下

1、从表X中读取一行记录R

2、从记录R中取得字段a到Y表中匹配

3、取得Y表中匹配的行与记录R组成一行，作为结果集数据的一行

4、重复执行步骤1到3，直到表X全部记录扫描完毕

在整个执行过程中，驱动表X是全表扫描，为N，N为1000行，而对于被驱动表 Y而言，由于使用到了索引 a,时间为 2 * log2M(这里由于a是普通索引，要进行回表操作，所以是 2 * log2M),M为100行

所以整体执行时间为： N + N * 2 *log2M

从这里我们可以看出，N的影响因素更大，即驱动表更影响执行时间

结论：在 NLJ中 尽量使用 小表作为驱动表，效率更高。


假设被驱动表Y未使用到索引，这种情况如何？

当被驱动表Y未使用索引时，MySQL使用了一种 BNL算法

BNL(Block Nested Loop)

执行过程如下

1、将X表的记录扫描放入Join Buffer中，这里用的是select * 放的就是整条记录

2、扫描被驱动表Y表，将Y表的所有记录取出来与 Join Buffer中的记录进行比对，满足Join条件的，将其加入结果集

从explain中我们可以看到，驱动表X和被驱动表Y都进行了全表扫描，这个执行时间为 M + N,即1100

其中Join Buffer的联查匹配执行时间为 M * N，即 1000 * 100 = 10万行

值得注意的是 Join Buffer的比较是在内存中，所以性能没有我们想的那么差。

整体执行时间为： M + N + M*N

当从公式来看，无论是大表还是小表作为驱动表，执行时间都一样。

但是 Join Buffer的size是有限的，通常不能将驱动表一次性的放入，需要拆成多个size的块，这也是为啥叫做 Block Nested Loop的由来

这个时候，假设驱动表N需要拆分成 T次才能放入，由于Join Buffer的size是固定的，所以 N越大，T越大，即 T = λ*N, λ 为(0,1)

所以，在这个算法的执行过程中：

扫描行数是 N+λNM；

内存判断 N*M 次。

注意，当驱动表被分成T段时，被驱动表需要被读取T次，这个与MySQL的内存设计有关，这里不做深究。

**结论：**整体来看，当Join Buffer的大小不足以装下整个驱动表时，N影响更大，即使用小表作为驱动表更好。

但是令人头疼的是，在实际的业务中，往往需要 大表联查小表，因为大表意味着是核心数据表，是需要经常被查询的，并且通常使用的是 Left Join而不是 Join，如果使用的是NLJ那还好，有时候使用的就是 BNL，你还不能创建索引进行优化，因为 Left Join 联查的小表字段往往区分度达不到要求，那有什么其他的办法呢？

这里简要介绍一下两种优化思想


Join优化

MRR(Multi-Range Read)优化

Multi-Range Read 优化 (MRR)。这个优化的主要目的是尽量使用顺序读盘。

先说一下回表的概念

回表：InnoDB 在普通索引 a 上查到主键 id 的值后，再根据一个个主键 id 的值到主键索引上去查整行数据的过程。

​ 如果随着 a 的值递增顺序查询的话，id 的值就变成随机的，那么就会出现随机访问，性能相对较差。虽然“按行查”这个机制不能改，但是调整查询的顺序，还是能够加速的。

​ 因为大多数的数据都是按照主键递增顺序插入得到的，所以我们可以认为，如果按照主键的递增顺序查询的话，对磁盘的读比较接近顺序读，能够提升读性能。

这，就是 MRR 优化的设计思路。此时，语句的执行流程变成了这样：

  1. 根据索引 a，定位到满足条件的记录，将 id 值放入 read_rnd_buffer 中 ;
  2. 将 read_rnd_buffer 中的 id 进行递增排序；
  3. 排序后的 id 数组，依次到主键 id 索引中查记录，并作为结果返回。

开启MRR优化：set optimizer_switch=”mrr_cost_based=off”。

（官方文档的说法，是现在的优化器策略，判断消耗的时候，会更倾向于不使用 MRR，把 mrr_cost_based 设置为 off，就是固定使用 MRR 了。）

BKA(Batched Key Access)优化

BNL转BKA算法

其实BKA算法就是在 驱动表 join 被驱动表时，给被驱动表上添加索引。

需要注意的是 BKA算法是依赖于MRR优化的，你必须先开启MRR，因为BKA算法本质是 MRR + NLJ的合并处理。即先将 驱动表在Join Buffer的数据拿出来，根据主键索引的ID顺序排序，减少随机IO，再与被驱动表的索引进行匹配，最大化的减少随机读盘。

BKA虽好，但有一些情况是不太适合直接在 被驱动表上加索引的，假如下面这条SQL语句的执行频率很低，这就有点浪费资源了。

可以考虑创建临时表，插入where过滤后的数据，并创建索引 b即可。

这样的速度也会非常快

但是在企业那种ORM封装后是不可能使用这种语句的，建议在业务层 查询 where Y.b >1 and Y.b < 1000的数据ID存储到 hashset中，使用hash来比对，这样的效果也不会太差的

总体来看，不论是在原表上加索引，还是用有索引的临时表，我们的思路都是让 join 语句能够用上被驱动表上的索引，来触发 BKA 算法，提升查询性能。
