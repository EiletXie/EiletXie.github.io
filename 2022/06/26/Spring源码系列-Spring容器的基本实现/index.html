Spring源码系列-Spring容器的基本实现

发表于 2022-06-26 阅读次数： 本文字数： 8.5k 阅读时长 ≈ 8 分钟

前言：

Spring的容器是Spring的核心之一，也是IOC和DP思想的基础实现，但是对于容器是如何实现，如何容器中的Bean是如何加载，这些我都一知半解，乘着自己工作3年多后对学什么比较迷茫，新技术的学习在工作中没有应用场景很快就会被遗忘，那就沉下心来看看优秀框架的源码，夯实基础，慢慢前行吧。


1.Spring核心类的介绍

1.1、DefaultListableBeanFactory

DefaultListableBeanFactory是整个bean加载的核心部分，是Spring注册及加载bean的默认实现。

AliasRegistry: 定义对alias的简单增删改等操作。

SimpleAliasRegistry: 主要使用map作为alias的缓存，并对接口 AliasRegistry进行实现。

1.2、XmlBeanDefinitionReader

XML配置文件的读取是Spring中重要的功能，因为Spring的大部分功能都是以配置作为切入点的，那么我们可以从XmlBeanDefinitionReader中梳理一下资源文件读取，解析及注册的大致脉络。

首先我们看看各个类的功能。

  • ResourceLoader：定义资源加载器，主要应用于根据给定的资源文件地址返回对应的Resource。
  • BeanDefinitionReader： 主要定义资源文件读取并转换为BeanDefinition的各个功能。
  • EnvironmentCapable: 定义获取 Environment方法。
  • DocumentLoader:定义从资源文件加载到转换为 Document的功能。
  • AbstractBeanDefinitionReader： 对EnvironmentCapable、BeanDefinitionReader类定义的功能进行实现。
  • BeanDefinitionDocumentReader: 定义读取Document并注册BeanDefination功能。
  • BeanDefinitionParserDelegate：定义解析Element的各种方法。

XmlBeanDefinitionReader主要包含以下几步的处理：

1、通过继承 AbstractBeanDefinitionReader 中的方法，来使用 ResourceLoader将资源文件路径转换为对应的 Resource 文件。

2、通过DocumentLoader 对 Resource文件进行转换，将 Resource 文件 转换为Document文件。

3、通过实现接口 BeanDefinitionDocumentReader类对 Document进行解析，并使用 BeanDefinitionParserDelegate对 Element进行解析。

可以看这个方法： org.springframework.beans.factory.xml.XmlBeanDefinitionReader#loadBeanDefinitions(org.springframework.core.io.Resource)

疑问点： ThreadLocal<Set> resourcesCurrentlyBeingLoaded 为什么容器加载的资源是单线程隔离的？它的读取使用场景是怎样的，设计的好处？

2.1、配置文件封装

Spring的配置文件读取是通过 ClassPathResource 进行封装的，如 new ClassPathResource(“beanFactoryTest.xml”),那么ClassPathResouce完成了什么功能呢？

在Java中，将不同来源的资源抽象成URL,通过注册不同的handler（URLStreamHandler）来处理不同来源的资源的读取逻辑，但是URL没有默认定义相对Classpath或ServletContext等资源的hanlder。并且URL也没有提供基础的方法，例如检查当前资源是否存在，检查当前资源是否可读等。所以Spring对内部是使用的资源实现了自己的抽象结果： Resource接口封装底层资源。

new XmlBeanFactory方法会调用父类构造器，其中ignoreDependencyInterface方法会忽略几个我们眼熟的接口。

这个方法是用来忽略给定接口的自动装配功能。这样做的目的是什么？

举个栗子： 例如 类A有属性B，那么初始化A时，会初始化B，但是有时候我们不想通过new的形式来初始化，而是通过上下文Aplication来自动装配注入，这样的好处是节省资源开销，尤其是在Spring中单例思想盛行的情况下。当然在B中配置一个 BeanNameAware接口，使得初始化B的时候通过 BeanFactoryAware或者Aplication来进行注入，这种也是可行的办法。

2.2、加载Bean

插曲： 一种好的代码写法 在org.springframework.beans.factory.xml.XmlBeanDefinitionReader#loadBeanDefinitions(org.xml.sax.InputSource, java.lang.String)

loadBeanDefinitions方法中，加载bean之前需要做很多处理，例如资源校验，资源存储校验和存储集合初始化等操作，这些操作与该方法的核心语义关系不是很大，属于准备阶段的东西。

为了防止方法臃肿，那么可以新增doLoadBeanDefinitions来实际做方法语义操作，外面loadBeanDefinitions方法只做准备工作和try catch finally等无关又必须的操作。

3、获取XML的验证模式

3.1 DTD与XSD区别

DTD与XSD是两种常用的验证模式。

DTD(Document Type Defination): 文档类型定义，是一种XML约束模式语言。它用来保证XML文档格式是否正确，校验元素和标签是否使用规范。（DTD包含了 元素、元素间的定义规则，元素可以使用的属性等）

XSD(XML Schemas Defination): XML Schema描述了XML文档的结构，校验XML文档命令空间是否正确，语法机构是否符合要求。

所以这两种验证模式的核心区别是啥？

我理解DTD是一种通用的XML的元素语法校验，它是以具体XML中 <!DOCTYPE 开头标注申明，Spring也是通过这个来判断是不是DTD的验证模式。而XSD是一种针对性的元素结构之间的关系校验。

4.1 EntityResolver 用法

官网这样解释：

如果SAX应用程序需要实现自定义处理外部实体，则必须实现loadDocument接口并使用setEntityResolver 方法向SAX驱动器注册一个实例。

EntityResolver 的作用是项目本身就可以提供一个如何寻找DTD声明的方法，即由程序来实现寻找DTD声明的过程。（就是我们把DTD文件放到项目的某个地方，然后实现时直接把这个文件读取返回给SAX，这样就避免了通过网络来寻找相应的声明。）

简单点说就是支持本地配置DTD的映射规则，并支持读取解析的这么个功能，从而优化了用户体验，快速加载。

不同的验证模式，Spring使用不同的解析器解析
