LLM之文档分块

前言：为了具体了解向量文档库的运行机制和文档分块的原理，我本地搭建了一个轻量的向量文档库进行测试和学习，可正常运行实现基础的所有核心功能。放在github上。需要的可拿去。 https://github.com/EiletXie/FileChunk

1、什么是文档分块

文档分块（Text Chunking）是构建大模型知识库（如 RAG 系统）的核心预处理步骤，其根本目标是：将长文档切分为语义完整、长度适中、利于检索与生成的文本片段（chunks），在保留上下文信息的同时适配模型输入限制。

2、为什么要文档分块

因为大模型存在限制因素：

模型上下文窗口有限 Qwen-Max 最多支持约 32k tokens，无法一次性处理整本书或长报告
向量检索需合理粒度 chunk 太大 → 检索噪声多；chunk 太小 → 丢失关键上下文
成本与效率平衡 过长的 prompt 增加 token 消耗和推理延迟

分块的本质： 在“语义完整性”与“技术可行性”之间找最优解

3、文档分块的原理

3.1 尊重自然语言结构

人类写作具有层级结构：文档 → 章节 → 段落 → 句子 → 词语
强制在段落/句子边界切割，比随机截断更保留语义

3.2 递归回退分割（Recursive Splitting）

主流算法（如 LangChain 的 RecursiveCharacterTextSplitter ）采用多级分隔符策略：
separators = ["\n\n", "\n", "。", "！", "？", "；", " ", ""]

工作流程 ：

  • 优先用最强分隔符（如 \n\n 段落）分割
  • 若某段仍超长 → 降级用次强分隔符（如 \n ）
  • 逐级回退直至满足长度要求
  • 相邻块设置重叠（Overlap）防止边界信息丢失

3.3 重叠机制（Overlap）

作用 ：避免关键信息恰好位于 chunk 边界被切断
典型值 ：50–200 字符（或 50–100 tokens）

示例 ：
Chunk 1: [A][B][C]
Chunk 2: [B][C][D] ← B/C 为重叠部分

🧩 模块一：文本预处理 —— 为分块做准备

1.1 文档解析（Parsing）

不同格式需不同解析器：

格式 推荐工具 注意事项
PDF（文字版） pdfplumber, PyPDF2 保留段落结构，避免乱码
PDF（扫描版） 阿里云 OCR / Tesseract + Layout Analysis 需识别标题、段落、表格位置
Word/PPT python-docx, unstructured 提取正文，忽略页眉页脚
HTML/Markdown BeautifulSoup, markdown 去除 script/style，保留语义标签
网页 Playwright + Readability.js 清洗广告、导航栏

✅ 关键目标 ：输出 纯文本 + 保留原始结构信息 （如 \n\n 表示段落）

主流分块策略对比：

策略 原理 优点 缺点 适用场景
固定长度分块 按字符/token 数硬切 实现简单，长度可控 易切断句子，语义断裂 日志、代码、结构化文本
按段落分块 以空行/标题为界 保留自然语义单元 段落长度不均，可能超限 小说、新闻、散文
递归分块（推荐） 多级分隔符+回退 平衡语义与长度 需调参 通用首选
语义分块 用 Embedding 计算句子相似度，在语义断点切割 最符合人类理解 速度慢，依赖额外模型 法律文书、学术论文
基于元数据分块 按文档结构（H1/H2标题、表格）划分 结构清晰，可溯源 依赖格式规范 技术手册、API文档

3.2 经验法则（基于任务类型）

任务类型 推荐 chunk_size (tokens) 说明
事实问答（FAQ） 150–300 一问一答简短
技术文档查询 300–500 需包含完整函数说明或参数表
法律条款检索 400–700 条款常跨多段
小说/散文阅读 500–800 允许叙事连贯性
表格/代码块 按结构整体保留 不要拆分

3.3 动态测试法（推荐）

  1. 准备 10–20 个典型用户问题
  2. 用不同 chunk_size（如 256, 512, 768, 1024）构建知识库
  3. 对每个问题：检索 Top-3 chunks
  4. 人工评估： 是否包含完整答案所需信息？
  5. 选择 召回率最高且 token 消耗最低 的配置

📊 示例结果：

  • chunk_size=256 → 60% 问题信息不全
  • chunk_size=512 → 90% 完整，平均 token=480
  • chunk_size=1024 → 95% 完整，但 token 翻倍 → 选 512

🔄 模块四：重叠（Overlap）机制详解

4.1 为什么需要 overlap？

防止关键实体在边界丢失

例：
Chunk 1: “张三毕业于清华大学，主修…”
Chunk 2: “…计算机科学与技术专业。”
若问题“张三的专业？”，仅 Chunk 2 无法回答

4.2 overlap 大小选择

chunk_size 推荐 overlap
≤ 300 30–50 tokens
300–600 50–100 tokens
≥ 600 100–150 tokens

⚠️ 注意 ：overlap 会增加存储量和检索计算量，需权衡

4.3 实现技巧（避免重复存储）

  • 存储时 ：每个 chunk 独立保存（含 overlap 内容）
  • 检索时 ：正常返回重叠 chunk
  • 生成时 ：大模型自动去重（因上下文连贯）

模块五：分块后的存储与索引

5.1 存储结构（以 Chroma 为例）

每个 chunk 存为一条记录：

{
  "id": "doc1_chunk3",
  "embedding": [0.23, -0.45, ..., 0.89], // 1024维向量
  "document": "这里是完整的chunk文本...",
  "metadata": {
    "source": "manual_v2.pdf",
    "page": 15,
    "chunk_index": 3,
    "start_char": 1200,
    "end_char": 1700
  }
}
