SKILL,MCP,Function Call概述

发表于 2026-03-06 阅读次数： 本文字数： 5.4k 阅读时长 ≈ 5 分钟

概念描述

Function Call

首先说最简单的Fuction Call,它是大模型推理阶段发出的一次指令，本质是一个结构化文本输出（例如JSON），对开发者和大模型都可见。例如开发者提供了一个查询天气的函数get_weather.当用户的prompt中有查询某地例如北京的天气等词组。则大模型推理阶段就会自动理解然后发出 get_weather所需的结构化文本({ "name": "get_weather", "arguments": { "city": "Beijing" } })给后台依赖，让它去调用对应的API，从而获取到结果加入注意力推理中。

它与API调用有一点类似，但本质不同，只是一次推理阶段的指令输出，具体动作是后台去调用的依赖第三方的，大模型只是发出指令，获取到结果加入上下文。

Q1：Function Call 一定要对应一个 API 吗？

不一定！它可以对应：

  • 一个 HTTP API（最常见）
  • 一个数据库查询
  • 一个本地 Python 函数（如数学计算）
  • 一个操作系统命令（如 list_files() ）

只要在系统中 注册了同名函数 ，LLM 就能“调用”它。

Function Call（LLM 输出） 对应的 API 调用（系统执行）
{ "name": "search_web", "arguments": { "query": "最新AI论文" } } GET https://api.bing.com/v7.0/search?q=最新AI论文
{ "name": "send_email", "arguments": { "to": "a@example.com", "body": "Hello" } } POST https://api.sendgrid.com/v3/mail/send with auth header
{ "name": "query_database", "arguments": { "sql": "SELECT * FROM users" } } 内部 JDBC/ODBC 调用（不一定是 HTTP，但仍是“外部接口调用”）

MCP

MCP（Model Context Protocol） 是 2024 年由 Anthropic、Databricks、Cohere、LlamaIndex 等多家公司联合提出 的新一代 模型与工具交互协议 ，旨在 替代或升级当前主流的 Function Calling（函数调用）机制 。

下面从 背景、核心思想、与 Function Call 的区别、优势、现状 等方面为你清晰解析 MCP。

✅ 一句话总结 MCP

MCP 是一个标准化的、双向的、支持多模态和流式交互的“模型-工具通信协议”，让 LLM 能像使用操作系统一样动态调用外部能力。

🔍 一、为什么需要 MCP？——Function Calling 的局限

当前主流的 Function Calling（如 OpenAI Tools、Google Function Calling）存在以下问题：

问题 说明
单向、一次性 LLM 输出一个 function call → 系统执行 → 返回结果。无法持续交互（如“翻页”、“追问”）。
静态注册 所有可用工具必须在请求前预定义（ tools= ），无法动态发现新工具。
仅限文本 难以传递图像、音频、结构化数据等多模态内容。
无状态 每次调用都是独立的，无法维护会话状态（如数据库连接、文件句柄）。
厂商锁定 OpenAI、Google、Azure 的格式互不兼容。

👉 MCP 就是为解决这些问题而生的通用协议 。

二、MCP 的核心设计思想

MCP 借鉴了 操作系统和微服务架构 的理念：

类比 说明
LLM = 用户 / 应用程序 发起请求，消费服务
Tools = 系统服务 / Daemon 作为独立进程长期运行
MCP = IPC 机制（如 Unix Socket、gRPC） 定义标准通信格式

✨ 关键特性：

  • 双向流式通信（Bidirectional Streaming）
    • LLM 可以发起调用 → 工具返回部分结果 → LLM 再发指令（如“加载下一页”）
    • 支持实时交互（如代码解释器逐步输出）
  • 动态服务发现（Service Discovery）
    • 工具可随时注册/注销，LLM 可查询“当前有哪些可用工具”
  • 多模态原生支持
    • 可传递文本、图像、表格、二进制数据等
  • 基于标准协议（如 gRPC 或 WebSocket）
    • 语言无关，跨平台
  • 上下文感知（Context-Aware）
    • 工具可访问当前对话上下文、用户权限等元信息

三、MCP vs Function Call 对比

维度 传统 Function Call MCP
通信模式 请求-响应（Request-Response） 双向流（Streaming）
工具注册 静态（请求前定义） 动态（运行时发现）
数据类型 主要 JSON 文本 多模态（文本、图像、文件等）
状态管理 无状态 有状态（可维护会话）
协议标准 各家私有（OpenAI/Google 格式不同） 开放标准（社区共建）
典型场景 查天气、发邮件 代码解释器、数据库探索、实时数据分析

SKILL

一、Skill 是什么？——本质定义

Skill 是一个封装了完整业务逻辑的、可复用的、面向任务的能力模块。
它代表 LLM “能做什么”，而不是“怎么调用”。

二、快速理解

Skill 是一个封装了端到端业务逻辑的能力单元。它可以通过两种方式被 LLM 使用：
1.静态注册模式：将其元信息（名称、描述、参数）注入 LLM 上下文，LLM 通过 Function Call 触发，由本地 Orchestrator 执行；
2.动态服务模式：将其暴露为 MCP 兼容的服务，LLM 通过标准协议直接与 Skill 通信，实现松耦合、可扩展的智能体架构。
无论哪种模式，LLM 只负责“决策是否调用”，不参与实际 API 执行。

Skill 是一个 能力单元 的封装，它包含：

  • 输入解析（如何从自然语言提取参数）
  • 业务逻辑（可能调用 1~N 个内部/外部 API）
  • 输出生成（返回 LLM 可直接使用的自然语言）
  • 错误处理、日志、配置等非功能需求
  • 它通常以 类（Class）或微服务（Service） 形式存在，而不仅是“文件”。
    📌 Skill ≠ 单个函数，而是 端到端任务流水线。

三、Skill 与 Function Call / MCP 的关系

组件角色Skill 如何使用它Function CallLLM 的输出格式Skill 的name必须与 Function Call 的name一致，才能被触发MCP新一代通信协议Skill 可作为 MCP 服务长期运行，通过流式接口提供能力API 调用底层执行动作Skill 内部可包含 1~N 个 API 调用

🏗️ 四、主流框架中的 Skill 实现

  1. Semantic Kernel（微软）——最规范的 Skill 设计
  • Skill = 文件夹
  • Function = 文件中的方法
  • 注册后，LLM 可调用 EmailSkill.send 或 CalendarSkill.create
    ✅ 优势：天然支持命名空间、版本管理、依赖注入

2. LangChain —— 用 Tool 模拟 Skill

  • 每个 @tool 函数 ≈ 一个轻量级 Skill
  • 复杂 Skill 需组合多个 tools + 自定义 Agent

3. LlamaIndex —— Skill 作为 Query Engine

  • 支持将整个 RAG pipeline 封装为一个 Skill

4. MCP 时代 —— Skill 升级为独立服务

  • Skill 作为独立进程运行
  • 通过 MCP 协议与 LLM 通信
  • 支持动态发现、热更新
    🌟 未来趋势：Skill = 微服务，MCP = 服务网格

五、什么时候该用 Skill？

场景 是否需要 Skill
简单工具调用（查天气、搜网页） ❌ 直接用 Function Call + 单函数即可
多步骤任务（订机票=查+比+付） ✅ 必须封装为 Skill
需要状态维护（数据库会话） ✅ Skill 可持有连接池
能力复用（多个 Agent 共享） ✅ 抽象为 Skill 模块
需要单元测试/监控 ✅ Skill 是天然的测试单元

💡 六、最佳实践建议

1.命名规范：{domain}_{action}，如 email_send, calendar_create
2.输入输出标准化：尽量返回自然语言（非 JSON），便于 LLM 理解
3.错误处理：捕获异常并转化为用户友好提示
4.可观测性：记录 Skill 调用日志（用于分析 LLM 行为）
5.安全边界：Skill 是权限控制的关键点（如“不能删除邮件”）
